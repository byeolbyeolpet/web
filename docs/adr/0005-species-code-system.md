# ADR-0005: 종 코드 체계 — 입도는 "병원이 갈리는 단위", 품종은 breeds

- 상태: 채택
- 날짜: 2026-07-23
- 관련: [#7](https://github.com/byeolbyeolpet/web/issues/7), CLAUDE.md "정체성", `supabase/migrations/20260723083200_species_sort_order_and_seed.sql`

## 맥락

`species` 테이블이 비어 있어 아래가 전부 FK 위반으로 막혀 있었다.

| 참조처 | 용도 |
|---|---|
| `pets.species_code` (NOT NULL) | 펫 등록 |
| `place_species.species_code` | **장소 × 종 태깅 = 해자** |
| `reviews.visited_species_code` | 후기의 방문 종 |
| `posts.species_code` | 커뮤니티 글 종 필터 |
| `dex_articles.species_code` | 사전 문서 |

즉 코드 하나가 다섯 소비처를 동시에 만족해야 한다. 그리고 이건 **단순 데이터가 아니라 제품 결정**이다 — "별의별 반려동물이 다 여기에"가 정체성이므로 **초기 목록에 특수동물이 얼마나 성의 있게 들어가느냐가 곧 해자의 폭**이다.

핵심 긴장은 입도(granularity)다. 두 소비처가 반대 방향을 당긴다.

- **병원 태깅**은 거친 쪽을 원한다. 병원은 "파충류 진료 가능"이라고 표기하지 "비어디드래곤만 진료"라고 하지 않는다.
- **펫 등록**은 세밀한 쪽을 원한다. 사용자는 "우리 레오파드게코"라고 부른다.

## 결정

**`species` 의 입도는 "이 종을 진료할 수 있는 병원이 실제로 갈리는 단위"에 맞춘다. 그보다 세밀한 것은 `breeds` 가 받는다.**

두 층으로 나뉘므로 긴장이 해소된다 — `species='lizard'` + `breed='레오파드게코'`.

- 코드 명명: **영문 소문자 + 스네이크**(`guinea_pig`). 쿼리 파라미터에 그대로 실리고 TS 유니온에서 읽기 좋다.
- `group`(coarse, enum `dog`·`cat`·`exotic`)은 이미 있던 축이다. `code`(fine)와 직교한다.

### 초기 14종

| group | code |
|---|---|
| `dog` | `dog` 강아지 |
| `cat` | `cat` 고양이 |
| `exotic` | `rabbit` 토끼 · `hamster` 햄스터 · `guinea_pig` 기니피그 · `chinchilla` 친칠라 · `ferret` 페럿 · `hedgehog` 고슴도치 · `sugar_glider` 슈가글라이더 · `bird` 조류 · `turtle` 거북 · `lizard` 도마뱀 · `snake` 뱀 · `amphibian` 양서류 |

경계 판단은 **2단 규칙**이다. 새 종을 추가할 때도 이 순서로 묻는다.

**1차 규칙 — 진료할 수 있는 병원이 갈리는가:**

- **`snake` 를 `lizard`·`turtle` 과 분리**: 뱀을 못 보는 병원이 실제로 많다. "파충류"로 묶으면 사용자가 헛걸음한다.
- **조류를 `bird` 하나로 묶음**: 앵무·문조·카나리아는 같은 병원이 본다. 품종은 `breeds` 로 내린다. `parrot` 을 형제로 두는 안도 있었으나 `parrot` 과 `bird` 는 형제가 아니라 포함 관계라 논리가 어긋난다.
- **`fish`·`insect` 제외**: 병원·미용·호텔 지도가 1차 가치인데 관상어·곤충은 거기 안 걸린다. 시드는 마이그레이션이라 나중에 사전을 만들 때 행만 추가하면 된다.

**명시적 예외 — 사용자 검색 인식이 완전히 갈리면 병원이 같아도 쪼갠다:**

- **설치류**(`hamster`/`guinea_pig`/`chinchilla`)가 이 예외다. 같은 병원이 보더라도 사용자 인식이 완전히 다르다 — `rodent` 하나면 "우리 기니피그 봐주는 병원"을 못 찾는다. 검색 정확도가 해자의 실체다.
- 예외는 좁게 유지한다. "인식이 다르다"만으로 무한정 쪼개면 1차 규칙이 무의미해진다 — 예외 추가는 이 ADR 에 근거를 덧붙이는 것을 조건으로 한다.

### `sort_order` 컬럼 추가

노출 순서를 데이터로 갖는다. `name_ko` 가나다순이면 가장 흔한 특수동물(토끼·햄스터)이 맨 아래로 밀린다. **종은 코드의 차이가 아니라 데이터의 값**(CLAUDE.md)이므로 순서도 코드가 아닌 DB 에 둔다. 10 단위로 띄워 중간 삽입 여지를 남겼다.

인덱스는 만들지 않았다. `analyze` 후 실제 실행계획이 `Seq Scan + Sort`(버퍼 1, 0.1ms)다 — 14행짜리 테이블에서 인덱스는 영영 안 쓰이면서 어드바이저에 `unused_index` 로만 남는다. (한 번 만들었다가 실측 후 제거: `20260723083550_drop_species_sort_order_idx.sql`)

## 결과

**긍정**
- 병원 태깅이 감당 가능한 크기로 유지된다. 태깅이 부담스러우면 아무도 안 채우고, 안 채우면 해자가 없다.
- 검색이 사용자 언어와 맞는다 — "페럿", "고슴도치"로 바로 찾힌다.
- 종을 늘리는 데 DDL 이 필요 없다. 행 추가(마이그레이션)뿐이다.

**부정 / 트레이드오프**
- **경계가 애매한 종이 생긴다.** 예: 프레리독·다람쥐·팬시랫은 어디에? 지금은 없다. 넣을 때마다 "병원이 갈리는가"를 다시 물어야 한다.
- **`breeds` 가 비어 있으면 반쪽이다.** `species='lizard'` 만으로는 "레오파드게코"를 표현할 수 없다. `pets.breed_id` 가 nullable 이라 당장 막히진 않지만, 펫 등록 UI 를 만들 때 품종 시드가 함께 필요하다.
- **병원이 "특수동물 진료"라고만 표기한 경우** 어느 코드를 붙일지 우리가 판단해야 한다. 공공데이터에는 이 정보가 없어 자체 태깅 비용이 든다 — 이게 해자의 실제 비용이다.

## 고려한 대안

- **거친 묶음 6개**(`rodent`·`rabbit`·`bird`·`reptile`·`amphibian`·`other`): 병원 태깅은 제일 편하지만 사용자가 "우리 페럿 봐주는 병원"을 못 찾는다. 검색 정확도를 잃으면 "종을 안 가린다"는 정체성이 말뿐이 된다. 배제.
- **종 단위 30개+**(`bearded_dragon`·`leopard_gecko`·`ball_python`·`syrian_hamster`): 검색은 정확해지지만 병원 태깅 부담이 폭발하고 `breeds` 테이블과 역할이 겹친다. 두 층 구조가 있는데 한 층에 다 넣는 셈이라 배제.
- **enum 으로 종 관리**: 이미 [#4](https://github.com/byeolbyeolpet/web/issues/4)에서 배제됐다. 새 종마다 DDL + 타입 재생성이 필요해 "종을 안 가린다"와 정면 충돌한다. `group` 만 enum 으로 남기고 `code` 는 테이블이다.
- **표시 순서를 프론트 상수 배열로**: `species` 를 데이터로 두기로 해놓고 순서만 코드에 두면 종을 추가할 때마다 배열도 고쳐야 한다. 배제.
