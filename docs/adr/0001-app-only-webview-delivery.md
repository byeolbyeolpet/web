# ADR-0001: 앱-only WebView 배포 — web은 앱 화면 substrate

- 상태: 채택
- 날짜: 2026-07-21
- 관련: [0002](0002-static-export.md), [0003](0003-keep-nextjs-over-vite.md), CLAUDE.md, [design.md](../design.md) §1

## 맥락

초기 문서가 배포를 **"1차 타깃 웹(Vercel) → 최종 앱"** 으로 적어 두었다. 이 web-first 프레이밍 때문에 설계 중 **SEO·도메인·검색 유입**을 정당화 근거로 자꾸 끌어오게 됐고("dex를 SSG로 굽는 이유는 SEO"), 그때마다 "우리는 앱으로만 낼 건데 앱스토어에 SEO가 왜 필요하냐"는 근본 반문에 부딪혔다. 판단이 반복해서 흔들렸다.

실제 의도는 처음부터 **앱-only**였다. web은 별도 제품이 아니라 **앱에 뿌릴 화면 그 자체**다(사용자 표현: "Toss처럼").

## 결정

- 배포 대상은 **Capacitor WebView 앱 하나**다.
- web 빌드(Next Static Export 산출물)는 그 앱에 담길 **화면 substrate**일 뿐, 독립 웹사이트도 유입 채널도 아니다.
- 전달 방식은 **정적 번들 내장 + OTA(방식 B)**. 원격 URL을 웹뷰가 로드하는 방식(방식 A, Toss가 일부 사용)은 **앱 심사 반려 리스크**로 배제한다.
- 따라서 **SEO·도메인·검색 유입은 이 프로젝트의 관심사가 아니다.** 이후 어떤 결정도 SEO를 근거로 들지 않는다.

## 결과

**긍정**
- 판단 단순화: web-vs-앱 저울질과 SEO 정당화가 사라진다.
- 오프라인 동작 가능(화면이 기기에 내장).
- 심사 리스크가 큰 원격 URL 방식을 피한다.
- 단일 코드베이스가 web 빌드=앱 화면으로 직결.

**부정 / 트레이드오프**
- 구글 검색을 통한 자연 유입이 없다. 사용자 획득은 **ASO(앱스토어 최적화) + 커뮤니티 + 입소문**에 의존한다.
- web 단독 사용성(브라우저로 방문하는 사용자)은 부차적 관심사다.

**참고 — 포트폴리오 데모**: 같은 정적 산출물을 Vercel 등에 올려 채용 담당이 설치 없이 클릭해 볼 **데모 링크**로 쓰는 것은 무방하다. 이는 호스팅 편의이지 "web을 제품 채널로 되돌리는 것"이 아니다.

## 고려한 대안

- **방식 A(원격 URL 웹뷰)**: 심사 없이 즉시 업데이트가 강점이나, 앱 핵심 화면을 원격에 두면 심사 반려 리스크가 커 배제.
- **web을 독립 제품 + SEO 채널로**: 앱-only 의도와 불일치. 이 프레이밍이 반복 혼란의 원인이었으므로 폐기.
